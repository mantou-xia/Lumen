# Lumen 共同开发手册

创建时间：2026-09-09

最后更新时间：2026-09-09

状态：已确认

## 目的与适用范围

本文定义 Lumen 后续共同开发时必须遵守的工程协作规范，覆盖任务开始、Git 分支与提交、模块边界、UI 组件复用、代码质量、测试验证、文档同步和评审交付。

本文不重新定义产品或技术架构。实现细节必须先服从相关架构文档；本文负责约束开发者如何在既有架构内安全、一致地完成变更。规则冲突时，按“用户明确要求 → 仓库级协作规则 → 已确认架构 → 本手册 → 局部实现习惯”的顺序处理，并在无法兼容时先澄清，不得静默绕过上层约束。

本文使用以下约束词：

- **必须 / 禁止**：不可省略的硬性要求；
- **应当 / 不应当**：默认执行，只有存在明确理由时才能例外；
- **可以**：在不破坏其他规则的前提下按任务选择。

## 开始开发前

每项开发任务必须按以下顺序准备：

1. 读取 [`README.md`](README.md)、本文及任务直接相关的已确认架构文档；因为实现必须基于当前公开事实，而不能只依赖对话或历史印象。
2. 检查工作区状态，识别并保留已有未提交修改；因为共同开发时无法确认的改动默认属于其他开发者。
3. 明确任务目标、非目标和验收方式；会显著改变产品范围或实现方向的歧义必须先澄清。
4. 非局部开发先在 `docs-local/plan/` 创建或更新计划，再开始修改；因为跨文件、跨模块工作需要可恢复的本地执行上下文。
5. 修改文件前重新读取其最新内容；因为共同工作区中的文件可能在任务期间被其他开发者更新。

计划只描述当前任务需要完成的工作，不得借机扩展未来能力。若执行方案会违反现有架构，应先提出冲突和更优方案，而不是用兼容层或临时分支掩盖根本问题。

## Git 分支规范

多人共同开发时，应当从最新的 `main` 创建任务分支，不在共享 `main` 上直接开发。一个分支只承载一个可独立说明和验证的目标；原因是单一目标更容易评审、回退和定位回归。

### 分支命名

统一格式：

```text
<type>/<scope>-<short-description>
```

`type` 只能使用：

- `feat`：新增或扩展用户能力；
- `fix`：修复缺陷；
- `refactor`：不改变外部行为的结构调整；
- `docs`：只修改文档；
- `test`：只新增或调整测试；
- `chore`：依赖、工具链或其他维护工作。

`scope` 优先使用稳定产品或技术模块：

```text
library | reader | learning | workspace | settings
content | runtime | api | infra | web | desktop | repo
```

命名要求：

- 全部使用小写英文、数字和连字符，不使用空格、下划线、中文或开发者姓名；
- `short-description` 描述结果，不写 `update`、`changes`、`temp` 等无信息词；
- 跨模块但目标单一时选择主责模块；确实属于全仓工程维护时才使用 `repo`；
- 不在分支名中堆叠多个模块名来代替任务拆分。

示例：

```text
feat/reader-pdf-renderer
fix/content-markdown-table-parsing
refactor/api-operation-errors
docs/repo-development-handbook
chore/repo-upgrade-typescript
```

## Commit 规范

提交信息统一采用：

```text
<type>(<scope>): <summary>
```

`type` 与分支类型保持同一集合，`scope` 使用本手册定义的模块名；纯全仓变更可以省略 scope。`summary` 使用简短祈使句或结果描述，不加句号。

示例：

```text
feat(reader): 支持 PDF 目录导航
fix(content): 修复 GFM 表格投影
refactor(api): 收敛 Operation 错误映射
docs(repo): 新增共同开发手册
```

每个提交必须满足：

- 只表达一个逻辑变更，代码、直接相关测试和必要文档应当一起提交；
- 不混入格式化、依赖升级或无关文件调整；
- 不提交密钥、本地数据、构建产物、调试输出或 `docs-local/`；
- 提交前检查差异，确认没有覆盖其他开发者的修改；
- 行为未完成或验证失败的工作不得用“完成”语义提交。

允许在一个任务分支内有多个可理解的提交，但禁止为了追求提交数量而机械拆分同一处不可独立验证的修改。

## 模块与依赖规范

模块职责与依赖方向以 [`0001`](0001-2026-09-06-product-and-system-architecture.md) 和 [`0008`](0008-2026-09-06-implementation-and-module-architecture.md) 为准。新增代码首先放入拥有该业务事实或交互职责的模块，不以“方便调用”为理由放进 `shared`、API Controller 或 Infrastructure。

### 模块归属

- 产品页面和交互按 `library`、`reader`、`workspace`、`learning-library`、`settings` 等能力组织；
- 文档格式解析、投影和位置映射属于 `content`；
- 跨领域 Use Case 编排属于 `application`；
- 表达、语境和 Recall 规则属于 `learning`；
- Prompt、Provider 调用和受控 Task 执行属于 `agent-runtime`；
- SQLite、文件、密钥和外部 Provider 适配属于 `infrastructure`；
- HTTP 路由、DTO 校验和错误映射属于 API 层，不承载业务决策。

### 依赖约束

- 跨模块调用必须通过已定义的 Contract、Port 或 Application Use Case，不直接导入对方内部实现；
- `packages/api-contract` 只承载协议 Schema、DTO 和稳定错误类型，不暴露数据库实体；
- 共享代码必须无明确业务所有者且被多个模块稳定复用，不能把 `shared` 当作临时代码存放区；
- 只有真实规模和独立依赖边界已经出现时才新增 workspace package，禁止提前创建空包或镜像目录；
- 循环依赖说明职责划分错误，必须调整所有权或抽取窄化 Contract，不使用动态导入掩盖。

上述约束的原因是保持模块化单体“部署统一、代码隔离”的设计：跨模块路径越显式，后续替换实现和定位数据所有权越可靠。

## 命名与代码组织

- React 组件、类和类型使用 `PascalCase`，函数、变量和 Hook 使用 `camelCase`，常量仅在真正不可变的模块级配置中使用 `UPPER_SNAKE_CASE`；
- React Hook 必须以 `use` 开头，事件处理函数优先使用 `handle<Action>`，传入组件的事件属性使用 `on<Action>`；
- 文件名沿用所在模块现有习惯：React 组件使用 `PascalCase.tsx`，普通 TypeScript 模块和样式使用小写语义名；同一目录不得混用多套命名风格；
- 名称表达领域含义，不使用 `data`、`manager`、`helper`、`utils2` 等无法说明职责的宽泛名称；
- 公共导出保持最小化，不因测试或调用方便暴露模块内部状态；
- 注释解释“为什么”和约束来源，不复述代码表面行为；临时兼容必须说明移除条件。

当一个文件同时承担协议转换、业务编排、持久化和界面状态中的多个职责时，应先按架构所有权拆分，而不是继续增加条件分支。

## UI 组件复用规范

Web 前端以 MUI 开源核心组件、`apps/web/src/app/ui.tsx` 共享入口和语义化 CSS Token 为统一基础。新增 UI 前必须按以下顺序决策：

```text
已有共享组件可满足
        ↓ 是：直接复用
        ↓ 否
MUI 基础能力可满足且多个页面会复用
        ↓ 是：在 app/ui.tsx 增加窄化封装或受控导出
        ↓ 否
是否属于单一产品能力的专用交互
        ↓ 是：放在对应能力目录内组合实现
        ↓ 否：重新检查需求或组件职责
```

### 必须遵守

- 业务页面优先从 `app/ui.tsx` 使用通用按钮、输入、选择、开关、滑块、卡片、提示和弹层表面；不得在页面中重复实现同类底层控件；
- `@mui/material` 的主题配置和通用视觉封装集中在应用 UI 层，业务页面不直接维护另一套 MUI Theme 或组件默认值；
- Reader Shell、Translation Lens、Recall、Workspace 和格式 Renderer 等产品专属交互保留在对应能力边界，不为了“复用”抽成失去业务语义的全局组件；
- 页面和业务组件只使用 `--ui-*`、`--reader-*` 等语义 Token，不写独立主题分支，不硬编码可主题化的颜色；
- 图标优先使用现有 `AppIcon` 和 Lucide 图标，不使用 Emoji、Unicode 字符或重复 SVG 充当功能图标；
- 交互组件必须提供可访问名称、键盘行为和正确语义；图标按钮必须有明确 `aria-label`；
- 组件 Props 只暴露调用方需要的语义选项，不把 MUI 全部配置无差别透传成新的隐式设计系统。

### 何时提升为共享组件

满足以下任一条件时，应当考虑进入 `app/ui.tsx`：

- 已在两个及以上产品能力中出现相同行为和视觉语义；
- 涉及主题、无障碍、焦点、弹层或状态反馈，需要统一行为；
- 属于产品级基础控件，后续页面应当以同一方式使用。

只在一个能力中出现、携带明确业务状态或依赖该能力数据模型的组件，应保留在能力目录。共享的判断依据是稳定职责，不是 JSX 长度。

## API、数据与安全规范

- API DTO 面向具体 Use Case，输入在 Transport 边界完成运行时校验，前端按稳定错误码处理；
- 数据库 Schema 或持久化语义变化必须通过迁移表达，并验证旧数据升级路径；
- 文件访问必须经过 Managed Filesystem 或受控 Resource API，不接受任意路径拼接；
- Provider 密钥和敏感配置只能由 Local Service Settings 与 Secret Store 管理；
- 导入文档始终视为不可信内容，禁止执行脚本、事件属性或绕过 Renderer 隔离；
- Electron 只提供有限平台能力，禁止让 Renderer 直接访问 Node、SQLite 或任意 IPC 通道。

这些要求属于安全和数据所有权边界，不得为了减少代码量而绕过。

## 测试与验证规范

验证必须与变更风险成比例，并优先运行最接近修改位置的检查。行为变化必须同步调整或新增测试；纯重构应保持既有行为测试不变。

最低验证要求：

| 变更类型 | 最低验证 |
| --- | --- |
| 纯文档 | Markdown、相对链接和 `git diff --check` |
| 单一前端组件或页面 | 对应测试、Web typecheck，必要时 Web build |
| Local Service 单模块 | 对应测试、Local Service typecheck |
| API Contract | Contract build/test，并验证直接消费方 |
| 数据库或迁移 | 迁移测试、Repository 测试和旧库升级路径 |
| 跨模块用户流程 | 相关单元/集成测试，并按风险运行 E2E Smoke |
| 发布或全仓基础设施 | 根目录 `check` 及发布所需人工验收 |

根目录标准命令为 `pnpm build`、`pnpm lint`、`pnpm typecheck`、`pnpm test` 和 `pnpm check`；Windows PowerShell 环境使用对应的 `pnpm.cmd`。不得声称未实际执行的验证已经通过；因环境或既有失败无法验证时，必须说明未验证项、原因和影响。

测试应验证对外行为和稳定 Contract，不应过度绑定私有实现。修复缺陷时，优先增加能复现根本原因的回归测试，而不是只验证补丁分支。

## 文档同步规范

- 产品边界、模块职责、依赖方向、持久化、AI 行为或用户可见流程发生非机械变化时，必须同步更新对应 `docs/architecture/` 文档；
- 开发协作方式、命名、UI 复用或验证门禁改变时，更新本文；
- `docs/architecture/README.md` 必须登记新的正式架构文档并提供正确加载路径；
- 计划、调研和实验过程只写入 `docs-local/`，公开文档不得链接或依赖本地文档；
- 不为普通开发任务自动创建报告，只有用户明确要求时才写 `docs-local/report/`；
- 文档结论与代码不一致时，不能只修改其中一边：先判断当前确认事实，再同步修正实现或正式文档。

## 评审与交付检查清单

提交评审或交付前，开发者必须确认：

- [ ] 变更只覆盖当前任务，没有夹带无关重构；
- [ ] 分支名和 Commit 信息符合统一格式；
- [ ] 新代码位于正确模块，没有反向依赖或跨层直连；
- [ ] 新 UI 已先检查共享组件，不存在重复底层控件、硬编码主题色或无语义图标；
- [ ] API、数据、文件、密钥和不可信内容没有突破既有安全边界；
- [ ] 行为变化有对应测试，执行过的验证结果可准确说明；
- [ ] 相关架构和索引已经同步；
- [ ] 已检查最终差异，并保留其他开发者的未提交修改。

不满足检查项时，应在交付说明中明确剩余问题和原因，不得用模糊表述将未完成工作包装为已完成。
