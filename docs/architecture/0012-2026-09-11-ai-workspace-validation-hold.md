# Lumen AI Workspace 场景验证与暂停扩展决策

创建时间：2026-09-11

最后更新时间：2026-09-11

状态：已确认

## 目的

本文记录 AI Workspace 在当前阶段的已实现能力、实际使用反馈、产品假设风险和暂停扩展决策。它是 Workspace 后续规划和开发的前置约束，直到真实使用数据足以支持新的场景定位。

本决策不删除、不回退已实现的 Workspace，也不在证据不足时直接将其改造为联网搜索或通用聊天工具。

## 与现有架构的关系

[`0011-2026-09-10-contextual-ai-workspace.md`](0011-2026-09-10-contextual-ai-workspace.md) 继续描述当前已实现 Workspace 的产品与技术事实，包括原文引用、文档上下文、Session、来源和持久化规则。

本文对后续开发优先级和产品扩展具有更高优先级：

- `0011` 中的现有 Contract 与数据不变量继续生效；
- 新增 Workspace 能力、改变默认回答策略或继续扩展引用交互前，必须先满足本文的恢复条件；
- 本文不宣布 `0011` 已废弃，因为已上线能力仍需被正确维护。

## 当前现状

Workspace 已经形成一套可运行的“当前文档问答”能力：

- 用户可以在 Reader 内打开 Workspace，并在同一 Document Revision 下使用多个 Session；
- 用户可以引用原文单词、连续词组、句子、语义块、翻译结果和历史问答；
- 对单词和词组引用，系统会从 Semantic Projection 补全所在句子作为直接语境；
- 无显式引用时，系统仍可以使用当前 Revision 的全文或 FTS 检索结果组建文档上下文；
- 回答遵循严格文档模式，不使用文档外部知识补答，依据不足时返回 `insufficient_evidence`；
- 回答、引用来源、上下文统计、Operation 和 Invocation 可以被追溯；
- Workspace 当前不使用互联网搜索、外部知识库或开放 Tool Calling。

上述现状说明 Workspace 的工程链路已经完整，但工程完整不等于产品价值假设已得到验证。

## 实际使用反馈

当前反馈暴露出，以“引用文档内容并严格依据当前文档回答”作为 Workspace 主价值，可能与真实英文阅读需求不匹配：

1. **普通单词的 Workspace 价值弱**

   用户对普通生词的首要需求通常是获得语境化翻译。现有 Translation Lens 已经拥有更直接、更低成本的交互，再将单词引用到 Workspace 中提问通常不产生足够的额外价值。

2. **句子需求更偏向定向讲解**

   用户在句子层面的障碍更可能是特殊搭配、语法习惯、句法主干、指代和隐含逻辑。这些场景需要结合所在句讲解，但不说明用户需要全文检索或复杂的多引用组合。

3. **大段原文缺少稳定的引用动机**

   整段引用容易导向翻译、总结或代读。如果用户只因为整段完全无法阅读而交给 AI，就可能偏离 Lumen 培养独立英文阅读能力的目标。段落上下文对指代、论证和前后关系仍可能有价值，但这一价值尚未经过真实使用验证。

4. **文档可见不代表文档能回答问题**

   许多阅读障碍源于作者默认读者已经掌握的背景知识。例如文章出现 `OOP` 却不解释该概念，用户需要的是根据当前句子消除歧义，再使用文档外知识补齐概念。严格文档模式在这类问题上反而无法完成任务。

5. **概念理解可能自然产生连续追问**

   用户理解 `OOP` 后，可能继续追问“还有哪些编程范式”。这类后续问题天然依赖上一轮语义，与现有“每轮默认独立、历史需显式引用”策略存在产品张力。

## 根本 Block

当前 Block 不是技术实现缺口，而是 **Workspace 的核心任务尚未经过真实阅读场景验证**。

目前无法有足够信心确认：

- Workspace 应继续以当前文档问答为主，还是改为“阅读障碍补全”助手；
- 普通模型知识、当前文档和 Web Search 分别应在哪些问题中使用；
- 什么粒度的原文上下文是必要的，什么引用交互对用户来说只是负担；
- 连续对话是概念理解的必要条件，还是会把用户带离当前阅读；
- 全文、检索段落、相邻句和显式引用各自的真实使用频率与价值；
- Web Search 是高频核心能力，还是只应在时效信息、专业查证和来源需求中按需启用。

如果在这些问题未明确时继续开发，很可能只会继续优化一个用户没有稳定需求的引用和文档检索流程。

## 暂停决策

从 2026-09-11 起，Workspace 进入“保留现状、暂停扩展、等待验证”状态。

### 暂停的工作

在恢复条件满足前，不继续：

- 扩展 Workspace 的原文引用粒度、多选区组合或引用操作复杂度；
- 为 Workspace 开发 PDF、DOCX、EPUB 等新格式的专属引用命中能力；
- 扩展全文问答、跨 BookPage、跨 Document 或全库问答；
- 为未经验证的问答场景增加 Embedding、向量数据库或更复杂的检索基础设施；
- 直接把 Workspace 改成开放式 Web Search、Tool Calling 或通用聊天平台；
- 仅为提高 Workspace 的功能数量而增加 Session 管理、生成式标题、对话分支等附属能力。

### 允许的工作

暂停扩展不等于放弃维护。仍然可以：

- 修复已实现 Workspace 的明确缺陷、安全问题、数据一致性问题和可访问性问题；
- 保持现有 Contract、迁移、持久化和已确认回归测试可用；
- 做不改变产品行为的必要兼容性维护；
- 记录真实阅读过程中的 Workspace 使用数据和用户反馈；
- 使用人工原型或一次性实验验证回答策略，但不将实验性结论直接固化为正式架构。

## 需要收集的证据

后续使用过程中，应围绕“用户为什么停止阅读”记录事件，而不只统计 Workspace 按钮点击量。

每个有效样本至少应能回答：

- 用户当时正在阅读什么，哪个内容引发了障碍；
- 障碍属于词义、搭配与语法、指代、句法、背景知识、论证逻辑还是其他类型；
- 用户当时自然产生的问题是什么；
- 用户实际选择了翻译、Workspace、普通 AI、网页搜索、词典、重读还是跳过；
- 解决问题所需的最小原文上下文是单词、完整句、相邻句、段落还是更大范围；
- 翻译、模型通用知识、当前文档或 Web Search 中哪一种信息来源真正解决了问题；
- 首次回答后是否产生自然追问，追问是否依赖上一轮语义；
- 获得帮助后，用户是否理解了原文并继续阅读，还是转入了与原文无关的长时间对话。

优先使用真实阅读观察、障碍日志和用户原始问题作为证据。“如果有某功能是否愿意使用”这类假设性问卷不能单独作为恢复开发的依据。

## 候选场景分类

数据收集时应按阅读障碍分类，不按“单词引用、句子引用、段落引用”等技术输入形式分类：

```text
词义障碍
语言形式障碍：搭配、语法、句法、指代和语用
背景知识障碍：专业概念、缩写、人物、事件和理论
推理与论证障碍：前后关系、作者立场和结论来源
延伸探索：从当前概念自然产生的关联问题
代读倾向：全文翻译、整章总结或跳过原文直接获得结论
```

这种分类可以先说明用户要解决什么，再决定需要什么上下文和工具，避免由已有的引用实现反向塑造需求。

## 恢复条件

Workspace 的功能扩展只有在以下条件满足后才能恢复：

1. 收集到多次真实英文阅读过程中的障碍事件，而不是只有功能偏好或团队推演；
2. 至少一类障碍在不同用户或不同阅读任务中重复出现；
3. 能明确说明该障碍的触发条件、用户目标、最小必要上下文、所需知识来源和理想回答边界；
4. 证据表明现有翻译、重读或普通搜索无法以同等或更低成本解决问题；
5. 经过 AI 帮助后，用户在大多数有效样本中能够回到原文并继续阅读；
6. 新方案不会把 Lumen 变成全文代读工具或通用聊天平台；
7. 在正式开发前，将验证结论更新为新的已确认架构决策，明确替代或修订本文和 `0011` 的相关结论。

这些条件的目的不是要求大规模统计显著性，而是防止再次仅根据“理论上可能有用”的假设扩展产品。

## 当前不做的决策

本阶段不预先确定：

- 不预先确定 Workspace 最终应是“严格文档问答”还是“语境化学习助手”；
- 不预先确定 Web Search 是默认必用、模型自动选择还是用户显式启用；
- 不预先确定对话历史应自动携带到什么程度；
- 不预先确定原文引用应保留为独立模式，还是收敛为选中后的直接问答入口；
- 不因为当前已经投入了开发成本，就默认现有产品形态必须继续扩展。

## 开发者执行规则

后续任何涉及 Workspace、原文引用、文档问答、多轮会话、外部知识或 Web Search 的任务，必须同时读取 `0011` 和本文。

开发前必须先判断任务属于：

```text
明确缺陷或必要维护
    → 可按现有架构执行

用户使用数据收集或人工验证
    → 可执行，但不得将未验证结论写成正式产品事实

新能力、新默认策略或扩大适用范围
    → 暂停，先检查恢复条件和新的架构决策
```

对任务性质无法明确判断时，必须先澄清，不得以“小优化”名义绕过本阶段的暂停决策。
